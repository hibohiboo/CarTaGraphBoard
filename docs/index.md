# 進み具合

初めての人・間が空いた人は、先に [はじめに](start.md) を読む。

> **3行で**
> 1. 設計は、下のフェーズ（0〜5）を順に進める。進んだかは、作ったファイルの数ではなく、各フェーズの**終える条件**のチェックの数で測る。
> 2. 条件を全部満たしたら、人間が確かめて次のフェーズへ進む。
> 3. チェックを付ける・外すのは人間。AI は「満たしたと思う」根拠を添えて頼む。

**いまのフェーズ：1. コンセプト**

## 0. 下準備

リポジトリと進め方を用意する。

- [x] 進め方（設計サイクル・ふりかえり・体制の進化）を書いた — `docs/process/`
- [x] 前のリポジトリのふりかえりを書いた — `docs/cycles/2026-11-01-C0-下準備.md`
- [x] 人間が進め方を読み、このまま始めてよいと確かめた

## 1. コンセプト（なぜ遊ぶのか）

ゲームの価値を決める。RDRA の「システム価値」、DDD の「コアドメインを見極める」に当たる。

- [x] 体験の核を1文で言える — `design/vision.md`「体験の核」
- [ ] デザインの柱が3つ前後あり、判断に迷ったときの物差しになる — 同「デザインの柱」
- [x] 遊ぶ人・人数・時間・場面が決まっている — 同「遊ぶ場面」
- [x] 「遊んで育つ（進化）」が、ボードゲームとして何で表されるかの方向が決まっている — 同「進化の表し方」
- [ ] やらないことが書いてある — 同「やらないこと」
- [ ] 前のリポジトリの要素を、柱に照らして「採る／捨てる／保留」に仕分けた — `decisions/`

## 2. 紙のプロトタイプ（何で、どう遊ぶか）

コンポーネントとルールを決め、紙で1回通して遊べるようにする。RDRA の「システム外部環境」（業務と利用シーン）、DDD の「ユビキタス言語」に当たる。

- [ ] 遊ぶのに要るものが全部、数とともに挙がっている — `design/components.md`
- [ ] 準備から終わりまで、ルールだけ読めば進められる — `design/rules.md`
- [ ] ルールに出てくる言葉が全部、用語集にある — `design/glossary.md`
- [ ] AI がルールだけを読んで、1回通しで遊んだ記録がある（詰まったところが問いになっている） — `playtests/`
- [ ] 人間が紙（か紙に近いもの）で1回遊んだ — `playtests/`

## 3. 試遊と調整（柱を満たしているか）

遊んで、柱に照らして直す。

- [ ] 柱ごとに「満たした」と言える試遊の記録がある — `playtests/`
- [ ] 遊びを止める問い（ルールが決まっておらず進めない）が `questions.md` に残っていない
- [ ] 人間が「これでボードゲームとして一通り完成」と判定した

## 4. ドメインモデル（デジタルにどう写すか）

紙のゲームを、そのままモデルに写す。RDRA の「システム境界」「システム」、DDD の「境界づけられたコンテキスト」「集約」に当たる。書き方は `model/index.md`。

- [ ] アクター・利用シーン・ゲームの流れ（業務フロー）が書いてある
- [ ] ルールの手順が全部、状態の遷移とイベントで書ける
- [ ] コンテキストの境界と、集約の候補が決まっている

## 5. 作るものを決める

- [ ] 何をデジタルにするか（全部か、遊びの補助か）と、最初に出す範囲が決まっている
- [ ] 技術と、実装の進め方（開発サイクル・検査の仕組み）が決まっている

ここまで来たら、実装の進め方を `docs/process/` に足す（前のリポジトリの開発サイクルを、そのとき要る分だけ持ち込む）。
