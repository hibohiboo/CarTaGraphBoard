# 体制の進化ログ

> **3行で**
> 1. 進め方の変更を「候補 → 評価 → 採用／却下」の型で記録する。却下も消さずに理由とともに残す。
> 2. 運用（誰が書き、誰が裁定するか）は [体制の進化](improve.md) が正。
> 3. 新しいものを上に書く。足したら、減らしたものも書く。

記録するのは進め方（手順・書き方・スキル・仕組み）の変更で、ゲームの設計の判断は `docs/decisions/` に書く。

このログが長くなったら（目安300行）、年ごとか月ごとのページに分ける。

この仕組みは前のリポジトリ（CarTaGraphFantasy・CarTaGraphAdventure の `docs/process/evolution.md`）から持ち込んだ。それより前の経緯はそちらにある。

## 書き方

- **候補** — `- [ ] <候補> — <気づいた状況>（<日付>）`。評価したら「採用」か「却下」へ移す。
- **採用・却下** — `### <日付> <題>` の下に、内容・理由・反映先と、次の3つを書く。新しいものを上に。
  - **きっかけ** — 誰が・何で気づいたか（ふりかえり／試遊／作業中の失敗／人間の要望）
  - **止め方** — どう防ぐか（仕組み／手順・書き方／置き場所）
  - **減らしたもの** — 足した分、何を減らしたか（[体制の重さの上限](improve.md#体制の重さの上限)）

## 採用

### 2026-11-01 1ラウンドの質問は3つまで、推奨の前に好き嫌いを聞く

設計サイクルの「詰める」に2つ足した（[設計サイクル](cycle.md)）。grilling スキルには、cycle.md に従う1行を足した。

- 1ラウンドの質問は、重要な順に3つまで。人間が一部の質問にだけ答え、確かめのラウンドが増えた（C3 で1回、C4 で2回）。数を絞り、全部に答えやすくする。毎回「答えの無いものは推奨で決めてよいか」と添える案は、黙っていると決まりやすく「決めるのは人間」と合わないので採らなかった
- 人間の好みで決まる問いは、推奨の前に、遊んできたゲームの好き嫌い（遊んでいる最中と遊び終えた後）を聞く。C3 で聞かずに推奨が外れ、C4 で聞いて15要素のうち13が推奨どおりに決まった。外れた2つは遊び終えた後の好みだった
- 反映先 … `docs/process/cycle.md`、`.claude/skills/grilling/SKILL.md`
- **きっかけ** — ふりかえり（C5。同じ種類が2回起きた） ／ **止め方** — 手順・書き方
- **減らしたもの** — なし。grilling の「フロンティア全体を1ラウンドで」を、このプロジェクトでは3つまでに狭めた（手順を足すのではなく絞る）

### 2026-11-01 スマホから docs を読めるようにする

`docs/index.html`（docsify を CDN から読む1ファイル）を置き、`docs/` を LAN に出して、スマホのブラウザで Markdown を読めるようにした。ビルドも検査もしない。上の候補「仕様書サイト（VitePress）とダッシュボード」は、読むためだけならこれで足りるので、候補のまま残す。

- 選んだ理由 … docsify は、開いたときにブラウザが `.md` をそのまま読んで表示する。HTML の写しを作らないので、中身の正は `.md` だけのまま（SSOT を崩さない）。ビルド・依存パッケージ・設定ファイルが要らず、`index.html` 1つで足りる。サーバーは Python 標準の `http.server` で、インストールが要らない
- 採らなかった案
  - **VitePress** — Markdown が正なのは同じだが、ビルドの工程と Node の依存が要る。前のリポジトリでは、ビルドに検査を足していって重くなった。読むためだけなら過ぎる
  - **GitHub にプッシュして、GitHub で読む** — いまリモートが無い。公開範囲を決める手間がかかる。Web 上に置くこと自体は、後で決めてよい
  - **claude.ai の Artifact に出す** — その時点の写しになり、`.md` を直すたびに出し直す。写しが SSOT を崩す
- 手で保つもの … 目次（`_sidebar.md`）はページへのリンクの一覧なので、ページを足したら直す。直し忘れても中身は食い違わず、目次からたどれないだけ
- 反映先 … `docs/index.html`、`AGENTS.md`「ディレクトリ」
- **きっかけ** — 人間の要望（C1 で、進め方をスマホから読んで確かめたい） ／ **止め方** — 置き場所（ビューア1ファイル）
- **減らしたもの** — なし（`docs/process/` の行数は増えない。ビューアは Markdown を読むだけで、書き方の決まりを増やさない）

### 2026-11-01 体制を作り直す（ボードゲームとして先に設計する）

前のリポジトリ（CarTaGraphFantasy・CarTaGraphAdventure）で、小さな機能ごとに8手順の開発サイクルを回し、ゲームの全体像が決まる前に1シーンずつ作っていたため、進みが見えにくく、文書と検査が膨らんで把握しづらくなった。新しいリポジトリで、外側（コンセプト）から内側（ルール → モデル → 実装）へ設計しきる形に作り直した。

- 持ち込んだもの … 進化ログ（候補 → 評価 → 採用／却下）、grilling で詰める手法、1か所に書く決まり（SSOT）、用語集、人間が裁定する点、仕組みで止める・2回目から仕組みにする・楽観的に進める原則、セッションを分ける、AI との協働の基盤（入口は AGENTS.md、モデルを固定しない）
- 新しく足したもの … フェーズと終える条件（`docs/index.md`）、問いの束で切る設計サイクル、仮決めで進む、2粒度のふりかえり、体制の重さの上限、DDD・RDRA とフェーズの対応
- 反映先 … このリポジトリ全体
- **きっかけ** — 人間の要望（前のリポジトリで進みが出ず、ステップを刻みすぎていると感じた） ／ **止め方** — 置き場所（新しいリポジトリ）と手順（設計の順番・終える条件・重さの上限）
- **減らしたもの** — 8手順の開発サイクル、3観点の AI レビュー、id 付きのブランチと PR、git フック、CI、VitePress と十数種類の検査、トレースの図、要望（バックログ）の1要望1ファイル（上の候補に残した）
