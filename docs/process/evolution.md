# 体制の進化ログ

進め方の変更を「候補 → 評価 → 採用／却下」の型で記録する。運用は [設計の進め方](index.md#体制の進化) が正。却下も消さずに理由とともに残す。

記録するのは進め方（手順・書き方・スキル・仕組み）の変更で、ゲームの設計の判断は `docs/decisions/` に書く。

このログが長くなったら（目安300行）、年ごとか月ごとのページに分ける。

この仕組みは前のリポジトリ（CarTaGraphFantasy・CarTaGraphAdventure の `docs/process/evolution.md`）から持ち込んだ。それより前の経緯はそちらにある。

## 書き方

- **候補** — `- [ ] <候補> — <気づいた状況>（<日付>）`。評価したら「採用」か「却下」へ移す。
- **採用・却下** — `### <日付> <題>` の下に、内容・理由・反映先と、次の3つを書く。新しいものを上に。
  - **きっかけ** — 誰が・何で気づいたか（ふりかえり／試遊／作業中の失敗／人間の要望）
  - **止め方** — どう防ぐか（仕組み／手順・書き方／置き場所）
  - **減らしたもの** — 足した分、何を減らしたか（[体制の重さの上限](index.md#体制の重さの上限)）

## 採用

### 2026-11-01 体制を作り直す（ボードゲームとして先に設計する）

前のリポジトリ（CarTaGraphFantasy・CarTaGraphAdventure）で、小さな機能ごとに8手順の開発サイクルを回し、ゲームの全体像が決まる前に1シーンずつ作っていたため、進みが見えにくく、文書と検査が膨らんで把握しづらくなった。新しいリポジトリで、外側（コンセプト）から内側（ルール → モデル → 実装）へ設計しきる形に作り直した。

- 持ち込んだもの … 進化ログ（候補 → 評価 → 採用／却下）、grilling で詰める手法、1か所に書く決まり（SSOT）、用語集、人間が裁定する点、仕組みで止める・2回目から仕組みにする・楽観的に進める原則、セッションを分ける、AI との協働の基盤（入口は AGENTS.md、モデルを固定しない）
- 新しく足したもの … フェーズと終える条件（`docs/index.md`）、問いの束で切る設計サイクル、仮決めで進む、2粒度のふりかえり、体制の重さの上限、DDD・RDRA とフェーズの対応
- 反映先 … このリポジトリ全体
- **きっかけ** — 人間の要望（前のリポジトリで進みが出ず、ステップを刻みすぎていると感じた） ／ **止め方** — 置き場所（新しいリポジトリ）と手順（設計の順番・終える条件・重さの上限）
- **減らしたもの** — 8手順の開発サイクル、3観点の AI レビュー、id 付きのブランチと PR、git フック、CI、VitePress と十数種類の検査、トレースの図、要望（バックログ）の1要望1ファイル（上の候補に残した）
