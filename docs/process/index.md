# 設計の進め方

> **3行で**
> 1. 外側（なぜ遊ぶのか）から内側（デジタルにどう写すか）へ、フェーズを順に進めて設計する。
> 2. 1回の作業は設計サイクル（問いを選ぶ → 詰める → 確かめる → 決める → ふりかえる）。AI が案と推奨を出し、人間が決める。
> 3. 進め方そのものも、ふりかえりの気づきから育てる（体制の進化）。重くしすぎないよう上限を置く。

このプロジェクトは、人間と AI エージェントが協働して、カルタグラフをボードゲームとして設計しきる。`docs/process/` が進め方の正（SSOT）である。なぜこの形にしたかは [C0 下準備](../cycles/2026-11-01-C0-下準備.md) と [DR-0001](../decisions/DR-0001-ボードゲームとして先に設計する.md) にある。

## 全体像

```text
フェーズ（docs/index.md）……終える条件を満たしたら次へ
  └ 設計サイクル（1回の作業）
      1. 問いを選ぶ
      2. 詰める
      3. 確かめる
      4. 決める
      5. ふりかえる ──▶ 体制の進化（候補 → 評価 → 採用／却下）
                               │ 進め方を直す
                               └──▶ 次のサイクルへ
```

## 設計の順番

外側（なぜ遊ぶのか）から内側（デジタルにどう写すか）へ決める。内側を先に決めると、外側が決まったときに作り直すことになる。

| フェーズ | 決めること | DDD・RDRA で言うと |
|---|---|---|
| 1. コンセプト | 体験の核・デザインの柱・遊ぶ場面・やらないこと | RDRA のシステム価値（アクター・要求）／DDD のコアドメインの見極め |
| 2. 紙のプロトタイプ | コンポーネント・ルール・用語 | RDRA のシステム外部環境（業務フロー・利用シーン）／DDD のユビキタス言語 |
| 3. 試遊と調整 | 柱を満たすまで直す | ドメインエキスパート（遊ぶ人）との対話 |
| 4. ドメインモデル | 状態・イベント・コンテキスト・集約 | RDRA のシステム境界・システム／DDD の戦術的設計 |
| 5. 作るものを決める | デジタルにする範囲・技術・実装の進め方 | — |

ボードゲームとして先に作るのは、紙のゲームが「業務」そのものだからである。紙で遊べる設計は、システムの都合（画面・保存・通信）が混ざっていないドメインモデルになる。デジタル化は、それを写す作業にする。

フェーズ1〜3の間も、DDD・RDRA のよいところは取り入れる。

- **用語は最初から用語集で決める**（ユビキタス言語）。ルールの文は用語集の言葉だけで書く。
- **関係でつなぐ**（RDRA）。ルールの各節は、使うコンポーネントと、誰がするのか（アクター）を明記する。
- **ゲームの流れはイベントの並びで書く**（イベントストーミング）。「〜した」の形で起きることを並べておくと、フェーズ4でそのまま写せる。
- **力を入れるところを選ぶ**（コアドメイン）。体験の核に効く部分を最も詰め、そうでない部分は既存のゲームの定番のやり方で済ませてよい。
