# 設計の進め方

このプロジェクトは、人間と AI エージェントが協働して、カルタグラフをボードゲームとして設計しきる。ここでは、1回の作業で回す**設計サイクル**と、サイクルの経験から進め方そのものを直す**体制の進化**を定める。この章が進め方の正（SSOT）である。

なぜこの形にしたかは [C0 下準備](../cycles/2026-11-01-C0-下準備.md) と [DR-0001](../decisions/DR-0001-ボードゲームとして先に設計する.md) にある。

## 全体像

```text
フェーズ（docs/index.md）……終える条件を満たしたら次へ
  └ 設計サイクル（1回の作業）
      1. 問いを選ぶ
      2. 詰める
      3. 確かめる
      4. 決める
      5. ふりかえる ──▶ 体制の進化（候補 → 評価 → 採用／却下）
                               │ 進め方を直す
                               └──▶ 次のサイクルへ
```

## 設計の順番

外側（なぜ遊ぶのか）から内側（デジタルにどう写すか）へ決める。内側を先に決めると、外側が決まったときに作り直すことになる。

| フェーズ | 決めること | DDD・RDRA で言うと |
|---|---|---|
| 1. コンセプト | 体験の核・デザインの柱・遊ぶ場面・やらないこと | RDRA のシステム価値（アクター・要求）／DDD のコアドメインの見極め |
| 2. 紙のプロトタイプ | コンポーネント・ルール・用語 | RDRA のシステム外部環境（業務フロー・利用シーン）／DDD のユビキタス言語 |
| 3. 試遊と調整 | 柱を満たすまで直す | ドメインエキスパート（遊ぶ人）との対話 |
| 4. ドメインモデル | 状態・イベント・コンテキスト・集約 | RDRA のシステム境界・システム／DDD の戦術的設計 |
| 5. 作るものを決める | デジタルにする範囲・技術・実装の進め方 | — |

ボードゲームとして先に作るのは、紙のゲームが「業務」そのものだからである。紙で遊べる設計は、システムの都合（画面・保存・通信）が混ざっていないドメインモデルになる。デジタル化は、それを写す作業にする。

フェーズ1〜3の間も、DDD・RDRA のよいところは取り入れる。

- **用語は最初から用語集で決める**（ユビキタス言語）。ルールの文は用語集の言葉だけで書く。
- **関係でつなぐ**（RDRA）。ルールの各節は、使うコンポーネントと、誰がするのか（アクター）を明記する。
- **ゲームの流れはイベントの並びで書く**（イベントストーミング）。「〜した」の形で起きることを並べておくと、フェーズ4でそのまま写せる。
- **力を入れるところを選ぶ**（コアドメイン）。体験の核に効く部分を最も詰め、そうでない部分は既存のゲームの定番のやり方で済ませてよい。

## 設計サイクル

1回の作業（1つのセッション）で1サイクルを回す。サイクルの記録は `docs/cycles/<日付>-C<番号>-<題>.md` に、[サイクルの記録の型](../cycles/index.md)で書く。

**サイクルの大きさは「問いの束」で切る。** 1つの小さな決定ごとに1サイクルにしない。いまのフェーズの終える条件のどれか1つを満たす（か、はっきり近づく）分の問いを束ねる。迷ったら大きめに取り、終わらなければ残りを次のサイクルに回す。

| # | ステップ | すること | 主体 |
|---|---|---|---|
| 1 | 問いを選ぶ | `docs/questions.md` と、いまのフェーズの終える条件から、今回決める問いを束ねる | AI が案を出し、人間が選ぶ |
| 2 | 詰める | 問いごとに案を2〜3出し、柱に照らした良し悪しを添えて推奨する。質問は `.claude/skills/grilling` の手法で、まとめて番号を振って聞く | AI が聞き、人間が答える |
| 3 | 確かめる | 決める前に、案で実際に遊べるかを確かめる。頭の中で1手番を通す・数を数える・簡単な表で試す。確かめたことと、確かめていないことを分けて書く | AI（人間も） |
| 4 | 決める | 人間が決める。結論を `docs/design/` に書き、理由と採らなかった案を `docs/decisions/` に書く。決めきれないものは「（仮）」で置いて問いに残す | 人間が決め、AI が書く |
| 5 | ふりかえる | サイクルの記録の「ふりかえり」を書く。進め方の気づきは [体制の進化ログ](evolution.md) の候補へ | 人間と AI |

**仮決めで進む。** 決めるための材料が試遊でしか得られないものは、仮に決めて先へ進む。完璧に決めてから次へ進まない。仮のものは「（仮）」と書き、試遊（フェーズ3）で確かめる。

**決める物差しは柱。** 案を比べるときは、まず [デザインの柱](../design/vision.md#デザインの柱) に照らす。柱で決まらないときは、「遊ぶ人にとって分かりやすいほう」「紙で扱いやすいほう」を取る。柱が決まる前（フェーズ1）は、体験の核の案に照らす。

**フェーズの外を先回りしない。** デジタルにしたときの都合（画面・保存・自動化）を、フェーズ3までの判断材料にしない。気づいたことは `docs/questions.md` の「後のフェーズ」に書いておく。

### セッションを分ける

1サイクル＝1セッションを目安にする。サイクルの終わりに、次に要ること（決めたこと・残った問い）を記録に書き終えてから、人間に新しいセッションを頼む。会話が長くなるほど、1回の操作で読み直す量が増えるため。

## ふりかえり

ふりかえりは2つの粒度で行う。

- **サイクルごと**（短く） — サイクルの記録の「ふりかえり」の節に、次の3つを書く。
  - **進んだか** — どの終える条件に、どれだけ近づいたか
  - **邪魔だったもの** — 時間を食ったこと、進め方の重さ、迷ったこと
  - **次に試すこと** — 次のサイクルで変えること
- **フェーズの終わり**（しっかり） — フェーズを終える前に、ふりかえりだけのサイクルを1回回す。KPT（続けること・問題・試すこと）で、そのフェーズのサイクルの記録を通して見る。設計の中身（柱がぶれていないか）と、進め方（重すぎないか、足りないか）の両方を見る。

## 体制の進化

遊んで育つゲームを作るのと同じく、進め方も気づきから育てる。

- **記録（誰でも）** — 「ルールが足りなかった」「邪魔だった」「話が通じなかった」に気づいたら、人間でも AI でも [体制の進化ログ](evolution.md) の候補に書く。
- **評価（人間が裁定）** — ふりかえりで、人間が採用／却下を決める。見る観点は、他のモデル・ツールでも回るか、1か所に書く決まり（SSOT）を壊さないか、手間に見合うか。
- **反映** — 採用したら `docs/process/` と `.claude/skills/` を直し、ログに日付・理由・きっかけを残す。却下も消さずに理由とともに残す。
- **仕組みにするのは2回目から** — 1回目の失敗は記録だけにする。同じ種類が2回起きたら、手順か仕組みにする。ただし、戻せない失敗（記録が消えるなど）は1回目から止める。
- **仕組みで止める** — 2回目の対策は、注意書きを足すより先に、機械で止める・自動で組み立てる仕組み（検査のスクリプト・git フック・Claude Code のフック）を考える。人や AI の注意力に頼る形は、担当やモデルが変わると崩れる。
- **楽観的に進める** — 前もって全部を防ごうとしない。後で気づいて戻せる失敗は、前で止める手順を足さない。

### 体制の重さの上限

前のリポジトリでは、進め方の文書と検査が中身より速く育ち、把握しづらくなった（[C0](../cycles/2026-11-01-C0-下準備.md)）。そこで重さに上限を置く。

- `docs/process/` の文書は、合わせて **400行以内**（`evolution.md` を除く）。超えそうなら、足す前に削るものを探す。
- 進め方を1つ足すときは、何を減らすか（減らせないなら、なぜか）を進化ログに書く。
- フェーズのふりかえりで、行数を確かめる（`wc -l docs/process/*.md`）。

## AI との協働の基盤

特定のモデルやツールが使えなくなっても回るように、次を守る。

1. **知識はリポジトリに置く。** 決まり・設計・理由・記録は `docs/` に書く。ツール固有の記憶（Claude Code の自動メモリなど）を正にしない。
2. **入口はツールに依存しない `AGENTS.md`。** `CLAUDE.md` はそれを読み込み、Claude Code だけの話を足すだけにする。
3. **ツール固有の層は薄く。** スキルは呼び出し口で、手順の本文は `docs/process/` に置く。
4. **モデルを固定しない。** 頼むときは等級（強い／標準／軽い）で考える。設計の判断・案出しは強い、記録の清書や用語の揃えは標準、探索や要約は軽い。
5. **人間が裁定する点を固定する。** 設計の決定、ルールと設計の矛盾、フェーズを終える判定、進め方の採用／却下は人間が決める。
